# 接口、鉴权与合规风险

本文件说明「真实模式」如何接入抖音 Web 端私信，以及必须知道的边界。

## 1. 一句话结论

抖音 **没有公开** 面向第三方的私信（IM）开放接口。市面上的第三方桌面客户端，走的都是
Web 端内部接口 + 登录态 Cookie + 前端生成的签名参数。这类接口：

- 无文档、无版本承诺，随时可能变更或下线；
- 受风控约束（频率、设备指纹、签名有效性）；
- 自动化访问可能违反《抖音用户服务协议》，存在账号被限制的风险。

因此本项目把「协议层」独立成可插拔适配器，默认使用**完全离线**的演示适配器，
真实适配器只提供**工程骨架**，不内置任何绕过风控的算法。

## 2. 请求链路

```
Renderer (React)
   │  IPC（contextBridge，白名单通道）
Main / ChatService
   │  ChatAdapter 接口
DouyinWebAdapter
   │  DouyinHttpClient（Cookie / 签名 / 限流 / 重试 / 错误归一）
   │  Signer（外部注入，本项目不提供实现）
Web 端私信接口
```

> 或 `url doesn't match`）。真实接口是 `imapi.douyin.com` + protobuf，见 §3.1。

## 3.1 真实接口（实测，2026-11-10）

宿主：`https://imapi.douyin.com`　编码：`application/x-protobuf`　鉴权：Cookie 会话

| 能力 | 方法 | 路径 | 实测 |
| --- | --- | --- | --- |
| 初始同步（会话+消息） | POST | `/v1/message/get_message_by_init` | 200，可解码 |
| 拉取用户消息 | POST | `/v1/message/get_user_message` | 200 |
| 按会话拉历史 | POST | `/v1/message/get_by_conversation` | 200 |
| 发送消息 | POST | `/v1/message/send` | 200（抓包中有） |
| 会话列表（含陌生人） | POST | `/v1/stranger/get_conversation_list` | 200 |
| 会话信息 | POST | `/v2/conversation/get_info_list` | 200 |
| 标记已读 | POST | `/v3/conversation/mark_read` | 200 |
| 已读索引 | POST | `/v3/conversation/get_read_index` | 200 |
| 最小索引 | POST | `/v3/conversation/get_min_index` | 200 |
| 成员已读索引 | POST | `/v1/conversation/batch_get_conversation_participants_readindex` | 200 |

响应外层信封（protobuf）：

```
#1 cmd（如 2043） #2 子命令（如 10001） #3 状态码 #4 状态文案（"OK"）
#6 扩展字段（字段号 = cmd），内含 payload
#7 logId #10/#11 服务端时间
```

单条消息字段（实测）：

```
#1 conversation_id  #3 message_id  #4 时间(µs)  #6 消息类型  #7 发送者 uid
#8 内容（JSON 字符串，含 text/createdAt 等）  #9 扩展 map（s:server_message_create_time 等）
```

会话字段：外层 `#1` 为会话 ID（私信为嵌套结构，群聊为 19 位数字串），`#3` 类型（1 私信 / 2 群聊），
`#6` 参与者，`#50` 详情（`#4` 秒级时间、`#5` 群名、`#6` 预览、`#7` 头像）。

用作者本人的 HAR 验证：**121 个会话（群 9 / 私信 112）、1504 条消息，发送者解析率 100%，
时间跨度 2025-11 → 2026-11**。

### 请求体是 protobuf，且抓包会被转码

Safari 导出的 HAR 会剥离 Cookie，并把二进制请求体按 UTF-8 转码（实测 `content-length: 772`，
HAR 中变成 788 字节），**无法直接回放**。Chrome 的 `Copy as cURL` 使用 `$'...'` 转义，可保留原始字节，
`npm run probe` 已支持该格式。

### 已经验证到哪一步

用最小 protobuf 信封（`#1=2001 #2=10020 #3="0.1.8"`，15 字节）直连上述端点，
服务端返回：

```
status_code=1, status_msg="unexepcted session length"
```

说明**请求格式已被接受**，卡在会话校验——只要提供真实的 `sessionid`，即可验证能否拿到数据。

### 当前接入状态（代码）

最终方案不是「自己构造请求」，而是 **`DouyinPageAdapter` + `ImWebBridge`（页面传输）**：

```
隐藏 BrowserWindow（partition: persist:douyin-im，已登录）
  └─ https://www.douyin.com/user/self?showTab=message
       └─ 页面自己带 token 请求 imapi.douyin.com（protobuf）
            └─ CDP：Network.loadingFinished → Network.getResponseBody
                 └─ ImCollector：按结构识别会话/消息（不绑定端点）
```

为什么必须这样：`empty token` 里的 token **不在 Cookie、不在 localStorage、也不在任何请求头**
（实测页面请求头只有 `Accept / Content-Type / Referer / User-Agent / sec-ch-ua*`），
它由页面脚本在发请求时写入 protobuf body。逆推它的生成算法成本高、易随版本失效，
而「让页面自己发、我们只读响应」既不需要 token，也不需要签名。

### 3.1.1 CDP 取响应体的四个坑（都踩过）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Network.enable` 永不返回 | 在 `about:blank` 上附加；子窗口 `sandbox: true` 在 `--no-sandbox` 宿主下 DevTools target 不可用 | 先真正加载 douyin.com 再附加；子窗口 `sandbox: false` |
| `No resource with given identifier` | 在 `responseReceived` 立刻读体，或并发 `sendCommand` 打乱会话 | 严格串行队列 + 只对白名单路径取体 |
| `No data found for resource` | 响应体还在流式传输 | 等 `Network.loadingFinished` 再 `getResponseBody` |
| 首屏数据总是丢 | 页面在首屏会客户端重定向，requestId 失效 | 首屏失败后 `reload()` 一次再采集 |

### 3.1.2 解码策略：不绑定端点

`ImCollector` 只按字段结构识别，因此对 `get_message_by_init`、`get_user_message`、
`stranger/get_conversation_list` 等**任何**返回会话/消息的响应都生效：

| 对象 | 判定条件 |
| --- | --- |
| 会话 | `fn1` 会话ID + `fn3` 类型 + `fn50` 详情 + `fn6` 参与者 |
| 消息 | `fn1` 会话ID + `fn3` 消息ID + `fn6` 类型 +（`fn8` 内容 或 `fn9` 扩展） |

昵称不在会话包里（参与者只有 uid + 头像），由 `ingestJson` 从页面其它 JSON 响应里
按 `uid/user_id` + `nickname` 结构抽取，按需回填；拿不到时退化为「抖音用户 + uid 后四位」。

### 3.1.3 已启用 / 未启用

- ✅ 会话列表、每个会话最近约 20 条消息、增量同步（页面轮询被捕获即入库）、好友（由私信反推）、昵称/头像
- ⛔ 发送、撤回、已读上报、拉黑、搜索 —— 请求体字段未验证，显式返回 `UNSUPPORTED`
- 实测规模：**121 会话 / 1504 消息 / 111 昵称**，消息与会话 ID 匹配率 100%

## 3.2 如何拿到真实端点

1. 浏览器登录 `douyin.com`，打开私信页面；
2. 开发者工具 → Network → 过滤 `im`（或 `message`）；
3. 在页面上点开一个会话、发一条消息，让请求出现；
4. 右键目标请求 → **Copy as cURL**；
5. 存成文件后回放：`npm run probe -- --curl ~/Desktop/req.txt --json`。

产物是一份**脱敏报告**（隐藏 Cookie 值与签名参数值，只保留 path、参数名、响应字段结构），
可直接贴回给我，用于修正 `endpoints.ts` 与 `wire.ts`。

## 4. 鉴权

### 4.1 Cookie 导入（真实模式唯一可用方式）

1. 在浏览器登录 `douyin.com`；
2. 开发者工具 → Network → 任意 `www.douyin.com` 请求 → 复制 Request Headers 的 `cookie` 整行；
3. 粘贴到客户端「Cookie 导入」。

客户端需要的关键字段：

| 字段 | 用途 |
| --- | --- |
| `sessionid` / `sessionid_ss` | 登录态主体，缺失则直接判定无效 |
| `ttwid` | 设备标识，回填到 query |
| `csrf_token` | 回填 `x-secsdk-csrf-token` 头 |
| `odin_tt` / `msToken` | 风控辅助字段，随 Cookie 一起透传 |

Cookie 用 Electron `safeStorage`（macOS 上由 Keychain 支撑的 AES-GCM）加密后写入
`~/Library/Application Support/抖音桌面聊天/secure/credentials.bin`，文件权限 0600。
渲染进程通过 IPC 只能拿到账号昵称/头像，**永远拿不到 Cookie 原文**。

### 4.2 签名参数

Web 端每个私信请求都会附带由页面 JS 计算的 `a_bogus` / `msToken` / `X-Bogus` 等参数。
本项目的 `Signer` 是一个注入点：

```ts
export interface Signer {
  name: string
  sign(input: { method; url; query; body?; userAgent }): Promise<Record<string, string>>
}
```

未注入时使用 `UnsupportedSigner`，请求在发出前即失败并返回可读错误：

> 抖音 Web 私信接口需要有效的签名参数（a_bogus/msToken）。当前未配置签名来源……

**这样设计的原因**：与其发出必然被风控拒绝的裸请求（可能加速账号异常），
不如明确告知「缺少合法签名来源」。本项目不提供、也不会内置签名逆向实现。

合法的签名来源由使用者自行解决，例如：具备资质的合作方、官方开放平台能力、
或在本机浏览器会话内复用页面自身脚本（需自行评估协议风险）。

## 5. 错误码归一

| 场景 | HTTP / status_code | 内部错误码 | 是否重试 |
| --- | --- | --- | --- |
| 登录态缺失/失效 | 401/403、8/10008/2154 | `AUTH_EXPIRED` | 否 |
| 频率限制 | 429、5/10015/10016 | `RATE_LIMITED` | 是（指数退避） |
| 服务端异常 | 5xx | `SERVER` | 是 |
| 网络中断/超时 | — | `NETWORK` | 是 |
| 响应非 JSON | — | `SERVER` | 否 |
| 缺少签名实现 | — | `UNSUPPORTED` | 否 |
| 业务校验失败 | — | `VALIDATION` | 否 |

请求侧还有一层保护：默认同一账号请求间隔 ≥120ms，超时 15s，最多重试 2 次；
同步引擎在连续失败时按失败次数线性退避（最多 5 倍间隔），不会打爆接口。

## 6. 合规与账号风险

使用真实模式前请确认你理解并接受：

1. **协议风险**：自动化访问 Web 私有接口通常不被平台协议允许，可能导致账号被限流、功能受限或封禁。
2. **数据风险**：客户端会把会话与消息缓存到本机 `state.json`（明文）。若设备多人共用，请自行加密磁盘。
3. **隐私风险**：导出功能会把聊天记录写成本地 Markdown，请注意存放位置。
4. **稳定性风险**：接口变更会导致功能失效，本项目不承诺跟进。
5. **不使用场景**：不得用于群发、营销、爬取他人数据、绕过平台限制等用途。

如仅需评估产品与技术方案，请使用默认的**演示环境**：它完全离线，
覆盖登录、会话、收发、撤回、好友、通知、导出等全部交互，且不触碰任何第三方服务。

## 7. 演示环境（Mock）说明

`MockServer` 在进程内模拟了一个「抖音私信后端」：

- 3 个会话（私信 ×3、群聊 ×1）、4 个联系人、7 条种子消息；
- 可注入延迟、抖动、限流、断网、登录态过期、发送失败；
- 支持扫码登录状态机（pending → scanned → confirmed）；
- 发送后可自动回复（默认开启，测试中关闭）。

它与真实适配器共用同一套 `wire.ts` 归一化逻辑，因此演示环境验证过的
解析、分页、去重、未读、通知等行为，在真实模式下走的是同一段代码。

## 8. 排障工具：`npm run probe`

用途：把「凭猜测写端点」改成「用真实请求校准」。支持三种模式：登录体检、HAR 全量端点清单、单条 cURL 回放。

### 8.1 登录体检（验证 Cookie 是否有效）

```bash
# 方式一：把 cookie 存到默认文件
echo '<粘贴 cookie 整行>' > ~/.douyin-chat-cookie.txt
npm run probe

# 方式二：指定文件（推荐，避免进入 shell 历史）
npm run probe -- --cookie-file ~/Desktop/dy-cookie.txt
```

它会打一个真实端点，输出 HTTP 状态、`status_code`、响应字段结构，并给出判定。

验证 IM 网关会话（最关键的一条）：

```bash
npm run probe -- --im-ping --cookie-file ~/dy-cookie.txt
```

- `status=0` → 会话可用，可以接只读真实模式；
- `status=1 / unexepcted session length` → Cookie 不完整或不是有效 sessionid；
- `HTTP 401/403` → 被拒绝，检查 Cookie 与 UA。
判定为 `AUTH`（`status_code=8`）说明 Cookie 无效或已截断；此时无需继续排查签名。

### 8.2 一次性发现所有端点（推荐：HAR）

比重放单条 cURL 更省事：让浏览器把整段操作里的请求都导出来。

1. 打开私信页面，操作一遍：点开会话、发一条消息、切到好友页；
2. DevTools → Network → 右键任意请求 → **Save all as HAR with content**；
3. 解析：

```bash
npm run probe -- --har ~/Desktop/douyin.har
npm run probe -- --har ~/Desktop/douyin.har --json > endpoints.json
```

输出示例：

```
共 23 个去重端点，其中 /im/ 相关 11 个

POST  /aweme/v1/web/im/xxxx/conversation/list/
      HTTP 200 · status_code=0 · 签名=a_bogus/msToken
      query: count, cursor, a_bogus, msToken
      body : count, cursor
      resp : status_code, conversations, has_more

POST  /aweme/v1/web/im/xxxx/message/send/
      HTTP 200 · status_code=0 · 签名=a_bogus
      body : conversation_id, content, msg_type, client_id
      resp : status_code, data
```

报告只含**路径、参数名、响应顶层字段名**，不含任何值、不含 Cookie、不含消息正文，
可直接分享。拿到这份清单，就能把 `endpoints.ts` 与 `wire.ts` 一次性校准。

### 8.3 回放单条抓包（验证某个请求）

```bash
npm run probe -- --curl ~/Desktop/req.txt
npm run probe -- --curl - < ~/Desktop/req.txt        # 从标准输入
npm run probe -- --curl req.txt --json > report.json # 机器可读，便于回传
```

输出示例（已脱敏）：

```
方式        POST /aweme/v1/web/im/xxxx/?…
Cookie      14 个字段：sessionid, sessionid_ss, ttwid, …
签名参数    a_bogus, msToken
第 1 次请求
  HTTP      200 · application/json · 231ms · 4821B
  业务码    status_code=0
  结构      { conversations: Array(12)<{…}>, has_more: boolean, cursor: number }
  判定      ✅ 接口返回成功
```

### 8.4 测签名有效期

```bash
npm run probe -- --curl req.txt --times 4 --interval 2000
```

若第 1 次成功、后续失败，说明 `a_bogus`/`msToken` 有时效（通常几分钟），
第三方客户端必须持续获得新的签名，不能只靠一次性抓包。

### 8.5 隐私边界

- 报告默认隐藏 Cookie 值与 `a_bogus`/`msToken`/`fp` 等签名参数值，只保留参数名；
- 默认不输出响应正文，只输出字段结构；
- 需要看正文时加 `--show-body`，此时报告**不可外发**（可能含聊天内容）；
- 工具只向 `www.douyin.com` 发请求，不经过任何第三方。

### 8.6 本工具不能做什么

- 不能生成签名（`a_bogus`），也不尝试绕过风控；
- 不能读取你浏览器的 Cookie（需要你手动导出）；
- 不能保证抓到的签名在几分钟后仍有效。
